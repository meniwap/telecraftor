# Contributing to Telecraft

Thank you for helping improve Telecraft. Small, focused pull requests with tests and clear release
impact are easiest to review.

## Before opening an issue

- Search existing issues and the documentation.
- Use the issue form that matches the request.
- Report vulnerabilities through the private process in [SECURITY.md](SECURITY.md), never in a
  public issue.
- Remove phone numbers, usernames, message content, API credentials, bot tokens, session data, and
  downloaded Telegram media from logs and reproductions.

## Development setup

Telecraft requires a supported CPython version. Create an isolated environment and install the
package with development tools:

```bash
python -m venv .venv
./.venv/bin/python -m pip install --upgrade pip
./.venv/bin/python -m pip install -e ".[dev]"
```

On Windows, use `.venv\Scripts\python` in place of `./.venv/bin/python`.

## Local checks

Run the same non-live checks expected for a pull request:

```bash
./.venv/bin/python tools/check_repo_hygiene.py
./.venv/bin/python -m ruff check src tests tools apps examples
./.venv/bin/python -m mypy src
./.venv/bin/python -m pytest tests/meta -q
./.venv/bin/python -m pytest -m "not live" -q
./.venv/bin/python -m pytest tests/live --collect-only -q
./.venv/bin/python -m build
./.venv/bin/python tools/check_repo_hygiene.py --artifacts
```

Ruff is the lint, import-order, and style checker configured by `pyproject.toml`; mypy runs in
strict mode outside generated TL code. Keep public APIs typed and add deterministic tests for
behavior changes.

## Live tests

Normal development and CI must not contact Telegram. Live tests are manual, opt-in, and require an
account controlled by the person running them. Follow [the live-test runbook](docs/11_live_runbook.md).
Never commit `.sessions/`, environment files, `reports/`, downloads, or captured protocol payloads.
Use synthetic fixtures unless a sanitized fixture is strictly necessary and reviewed for personal
or authorization data.

The only release-evidence exception is the filtered
`release/evidence/<version>/release_manifest.json` generated by `tools/release_check.py`, following
`docs/18_release_process.md`. Its companion `readiness.md` and all raw live reports remain local.

## Pull requests

1. Branch from the current `main` branch and keep the change focused.
2. Add or update tests and documentation.
3. Add a `CHANGELOG.md` entry for user-visible behavior.
4. Explain compatibility, security, and live-test impact in the pull request template.
5. Confirm that generated/build artifacts and credentials are not staged.

Changes to a stable API must follow [the support and deprecation policy](docs/17_support_policy.md).
Generated TL code should be regenerated through the repository tools rather than edited manually.

## Responsible Telegram use

Contributors and users must supply their own Telegram `api_id` and `api_hash` from an application
they control. Do not copy, publish, or share credentials from this project or another developer.
Use Telecraft only with accounts and chats you are authorized to access. Automated messaging,
scraping, userbots, and bots remain subject to the [Telegram API Terms of Service](https://core.telegram.org/api/terms),
applicable law, consent requirements, and Telegram rate limits. Spam, evasion of platform controls,
and abusive automation are not accepted project use cases.

By participating, you agree to follow [the Code of Conduct](CODE_OF_CONDUCT.md).
